# Application audit — 25 October 2026

## Verdict

We have a solid working prototype and a reasonable production design. There is no basis for claiming a “top 1%” submission: we do not know the other submissions, and this audit uncovered significant gaps that the existing passing tests did not detect. Before presenting the solution as exceptionally polished, address A1–A5 in particular and document complete business scenarios.

The strongest elements are brand permissions enforced outside the model, a restricted SQL compiler, exclusion of contact fields from SQL results, transactional confirmed deletion, shared cost/time limits, reproducible offline tests, and a clear distinction between the prototype and the HLD.

The main problem: “validated” currently means that selected references agree with query results and the restricted report format. It does not mean that the queries matched the user's intent, that all necessary data was included, or that every response path underwent this validation.

## Scope and method

- Reviewed runtime code, tests, README/QUICKSTART, HLD, requirement mapping, previous evaluation, and the “1-percent” plan.
- Baseline: local commit `53c9ff2` (`fixes`); the working tree was clean before the audit.
- Reran Ruff, formatting checks, strict Pyright, and the entire offline suite with coverage measurement.
- Ran additional controlled probes through the real ADK Runner with scripted model responses and a synthetic SQL executor; separately injected SQLite and logging failures.
- The probes did not read `.env`. They used a dummy key, temporary databases, and a substituted model transport. They did not send questions to Gemini/BigQuery or delete real reports.
- No new live tests, deployment, load tests, or UX evaluation with executive users were performed. Historical live results are from 22 October, not this audit.
- No application code was changed and none of the reported issues was fixed. This document records findings.

Commands executed:

```sh
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked pyright
uv run --locked pytest --cov=retail_agent --cov-report=term-missing -q
```

Result: **85 passed, 2 live deselected**, with no Ruff or Pyright errors. Reported combined statement/branch coverage: **88%**; `quality.py` 95%, `reports.py` 96%, `agent.py` 90%, CLI 61%. The warning about experimental ADK response-schema support remains. Coverage does not measure business correctness; the controlled probes below uncovered gaps despite the passing suite.

## How the application works

1. The user starts the local CLI and selects a demo identity: Alice, Bob, or CEO.
2. Library commands such as `/save`, `/read`, and `/confirm` execute in application code without the LLM.
3. For an analytical question, Gemini through Google ADK proposes a JSON plan: analysis type, period, grouping, filters, and ranking metric.
4. Pydantic checks the plan's structure. Application code adds user permissions and compiles parameterized SQL; the model does not submit arbitrary SQL for execution.
5. The BigQuery adapter performs a dry run, checks the scan limit, executes the query, and validates the result.
6. Results receive an evidence ID, scope, definitions, period, and job ID. Python calculates additional metrics.
7. The model selects metric references, hypotheses, and proposed actions. The validator checks the allowed format. Code builds the text from source values and templates.
8. An invalid analytical structure gets one application-level, tool-free repair attempt within the same budget. If it fails, the application shows verified figures with a warning.
9. The result appears in the terminal; saving it as a report requires an explicit command. Chat answers and diagnostics are stored locally. The model's conversation context is limited to the last four turns held in process memory.

**Caveat:** steps 7–8 apply to responses with fresh analytical results. A1 identifies a gap in other response paths.

## Validation: guarantees and limitations

| Layer | Actual control | Limitation |
|---|---|---|
| Input | Question length, known personal-data patterns, and control characters. | Does not recognize every name/address or all off-topic content. |
| Plan | Allowed fields/enums, date ranges, limits, and some filter compatibility checks. | Does not independently establish that the model selected the period and metric requested by the user. |
| Access | Code-owned permissions and brand filters before aggregation; roles do not come from model arguments. | Local demo without real authentication or production IAM. |
| SQL/PII | Restricted SELECT compiler, parameters, excluded prohibited fields, aggregate-only state data with at least five customers. | The parser is not a general proof of arbitrary SQL safety; a minimum of five does not guarantee resistance to aggregate differencing. |
| BigQuery | Dry run, byte limit, bounded rows, exact column set, and scalar types. | Does not establish the truth of the underlying dataset. |
| Report | Known metric/evidence references, compatible action measures, specified quarters, and churn-share target range. | A1–A3: category bypass, missing intent/completeness checks, and fragile date context. |
| Save/delete | Ownership, explicit save; exact deletion set, token, TTL, version, session, single use, and transaction. | Saving a report and its audit entry is not one transaction — A4. |
| Cost/failures | Attempt, cost, and time limits; bounded retries; no blind BigQuery job resubmission. | Some local failures are unhandled — A5; not every “repair once” rule has a separate enforced counter. |
| Developer tooling | Ruff, strict Pyright, pytest, and network blocking in standard tests. | Does not replace business-question evaluation or complete live E2E checks. |

## Findings

### A1 — high priority: factual validation bypass through `clarification`

Locations: [agent.py](../../src/retail_agent/agent.py), the `if evidence` condition around line 337 and handling of responses without evidence around lines 412–425.

**Reproduction:** real ADK Runner, scripted model response, zero tool calls:

```json
{"kind":"clarification","message":"Revenue was 999999 dollars."}
```

When asked about Q1, the application returned that exact text with `quality_status="not_applicable"`, without querying data. Separately, the `schema` path after a `schema_info` call also preserves the model's message instead of always substituting the application-owned description.

**Impact:** the model's response-category label cannot serve as a trust boundary. Fabricated facts or non-analytical content can be displayed. This demonstrates a gap using a controlled model; it is not a claim that Gemini produced this response in the latest demo.

**Remediation:** control every output path; generate schema and library descriptions in code; represent clarifications as constrained questions about missing parameters, without arbitrary factual answers. Test refusal, schema, and clarification paths, not only `kind=analysis`.

### A2 — high priority: correct data for the wrong period receives `validated`

Locations: [agent.py](../../src/retail_agent/agent.py), `run_analysis` and `check_draft`; [quality.py](../../src/retail_agent/quality.py), `validate_narrative` around line 264.

**Reproduction 1:** question “What was revenue for Q1 2026?”, scripted plan covering `2026-07-01`–`2026-10-01`, followed by reference `E1.r0.revenue`. On the fixture, the application returned Q3 revenue of 80 with `quality_status="validated"`. The period is explicitly visible, but the answer does not fulfill the request.

**Reproduction 2:** a request for a report with monthly trends and the top 10 products passed with a single total-revenue result and one action; `validate_narrative()` returned an empty issue list.

**Impact:** a reference proves the origin of a number, not its relevance to the question. There is no enforcement that the final summary includes both rankings, all months, the compared products, or verification of an alleged churn spike.

**Remediation:** introduce an explicit analysis contract maintained in state: periods, scope, expected outputs, and comparisons. Check plans before querying and evidence/selected-finding completeness before answering. Do not limit this to a regex recognizing one example phrase; ask for clarification when uncertain. Add evaluations for “correct numbers, wrong answer.”

### A3 — medium priority: report dates and requirements depend on the current message

Locations: [quality.py](../../src/retail_agent/quality.py), `action_window` around line 184 and `missing_actions` detection around line 273.

**Reproductions:**

- `Create a report for Q1 2026. Do not include actions.` → `missing_actions`, despite explicitly excluding actions.
- `Increase the proposed targets in that report` → `action_window=None`, even with Q1 evidence and a previous turn specifying Q2 actions. The previous structured periods are not an input to the validator.

**Impact:** ordinary follow-ups and wording variations can trigger unnecessary repair/fallback. Selected English quarter expressions are supported, rather than general conversation semantics. This is a product limitation, not a requirement to add every language to the assignment.

**Remediation:** retain analysis and action periods in typed conversation state; allow intentional overrides and section exclusion. Validate structured intent rather than the presence of the words `report`/`actions`.

### A4 — medium priority: report and audit saving is not atomic

Location: [reports.py](../../src/retail_agent/reports.py), `save()` around line 69; the connection uses autocommit (`isolation_level=None`).

**Reproduction:** a trigger rejecting INSERT into `audit` was added to a temporary database. `save()` raised a SQLite error, but the report count after the error was **1**. The report INSERT had already committed. The CLI may then say the operation was not confirmed, while retrying creates another report.

**Remediation:** use a transaction covering both save and audit, roll back on any failure, and test failure between writes. Consider an idempotency key for retries of the same command. **Deletion is not affected by this issue:** `confirm()` already has its own transaction and rollback tests.

### A5 — medium priority: logging failure can terminate chat

Locations: [observability.py](../../src/retail_agent/observability.py), file writing; [agent.py](../../src/retail_agent/agent.py), `trace.emit` around line 155 before the main `try`; [cli.py](../../src/retail_agent/cli.py), error handling around line 140.

**Reproduction:** replacing `Trace.emit()` with an `OSError` caused that exception to escape `Analyst.ask()`. The CLI loop catches `AppError` and `sqlite3.Error`, not `OSError`.

**Remediation:** define a diagnostics-failure policy: a controlled message or fallback sink without sensitive data, while keeping the CLI usable. Do not silently lose critical mutation audits; distinguish them from auxiliary logs. Add fault injection for permission-denied directories/full disks. Also inspect resource initialization and cleanup outside the protected section.

### A6 — medium priority: persistent diagnostics cannot reconstruct question intent

Locations: [observability.py](../../src/retail_agent/observability.py), [reports.py](../../src/retail_agent/reports.py) `append_chat`, and [agent.py](../../src/retail_agent/agent.py) `history`.

Logs intentionally exclude content, and the persistent `chats` table stores the answer, plan, and evidence but not the user's question. The question exists only in process memory. After a restart, execution and results can be inspected, but it may be impossible to establish why Q3 was the wrong answer to Q1. Fixed `policy=v1` and `compiler=v1` labels do not uniquely identify a prompt/release.

**Remediation:** retain a minimized intent contract and prompt/model/code versions linked to the trace ID. If message content is needed, use a separate redacted diagnostic store with restricted access and retention. Do not put raw prompts or PII into ordinary logs. The HLD describes this direction; the prototype does not yet implement it.

### A7 — product limitation: a very narrow vocabulary of findings and actions

Location: [quality.py](../../src/retail_agent/quality.py), `Hypothesis`, `ProposedAction`, `ACTION_TEXT`, and `HYPOTHESIS_TEXT`.

There are four hypothesis types and four action templates. This effectively limits hallucinations, but reports can resemble lists of numbers with generic advice. It does not establish a useful answer to “why?”. The model proposes targets; some units/ranges are checked, but economic rationale and feasibility are not. A recommendation with a valid reference can still be weak business advice.

**Remediation:** develop a small catalog of concrete, calculated findings: volume/average-price changes, category contributions, cohort composition, and changes in the churn denominator. Allow linguistic freedom only where meaning remains verifiable. Do not immediately substitute multiple agents or another LLM as the sole judge.

### A8 — UX and evaluation limitation: technical correctness is ahead of the executive experience

[render.py](../../src/retail_agent/render.py) always appends raw table-like lines, definitions, job IDs, and SQL hashes. Combined with repeated periods in the narrative, this exposes substantial technical detail. No evaluation with actual business users has been performed. The live test checks query presence, `quality_status`, the Q2 date, and section presence, rather than complete intent and numerical correctness for every scenario.

**Remediation:** make a short business summary the default, with details behind `/details` or a flag; use proper terminal tables; distinguish objectives, observations, hypotheses, and limitations. Create a small independently evaluated scenario set with follow-ups, period changes, false premises, empty data, and access denials. Split dependent live tests so a follow-up failure does not prevent churn testing.

## Architecture and assignment alignment

The HLD reasonably selects Cloud Run/FastAPI, Gemini/Vertex AI, BigQuery, Cloud SQL, Cloud Storage, Cloud Tasks, and telemetry. It does not add Kubernetes or a separate vector database unnecessarily. It explains transactions, distinguishes application permissions from IAM, and covers retention and backup issues. Production learning, personas, and Golden Knowledge are explicitly design-only, consistent with the accepted scope. The absence of a real bucket is not a missing client-required implementation.

Areas to clarify:

- The HLD response flow should explicitly include the current quality gate and its limits, rather than only “structured answer → user”.
- The BigQuery permissions description leaves a choice between per-scope identities and an equivalent gateway; select a concrete approach and explain identity propagation in the final presentation.
- Message-correspondence debugging is more fully designed than implemented; do not present it as complete prototype coverage.
- “One plan correction” and “one diagnostic for empty data” are primarily model instructions; the hard boundary is the overall attempt/query limit. Documentation should distinguish these mechanisms.
- The current README still has general statements about model prose that should be aligned with the restricted report language. Publication and CI execution status should be confirmed on GitHub; a local commit does not prove successful hosted CI.

## Existing strengths

- Brand filtering before aggregation and customer history; no model-controlled identity parameter.
- SQL restricted to a compiled language, parameterized values, and no arbitrary Python or SQL execution tool.
- Customer contact fields are excluded from results; source privacy relies on projection, not a subsequent request for the LLM to mask data.
- Separate CEO analytics permissions and private-report ownership.
- Exact-set preview, single-use token, TTL, versions, and a deletion transaction; the model does not receive the confirmation token.
- Dry runs, byte limits, recovery of the same job ID, and bounded retries.
- Synthetic data with independent expectations, state tests, fault injection, and a real ADK loop in offline tests.
- Honest documentation of ADK experience, uv dependencies, and design-only versus implemented features.

These are valuable engineering decisions. The audit gaps do not invalidate the whole project, but they prevent equating test count with business readiness.

## Plan for a strong submission

1. **Before the next demo:** close A1 and add regression cases for every response category.
2. **Business correctness:** introduce an intent and conversation-state contract; control incorrect periods, missing rankings, exclusion of actions, and follow-ups — A2/A3.
3. **Resilience:** make save+audit transactional and handle logging failures — A4/A5.
4. **Usefulness:** add concrete calculated findings and a simpler executive view — A7/A8.
5. **Evidence:** retain intent in diagnostics, use independent live scenarios and a small question holdout set. Complete the full demo with external credentials in a fresh environment, reporting quota limitations accurately.
6. **Submission:** keep HLD/README current, verify hosted CI, prepare a five-minute demo, and be ready to explain the tradeoff between restricted SQL/reporting and LLM flexibility.

Do not increase the number of frameworks, models, or services now. The greatest benefit will come from better intent alignment, local resilience, and the quality of decisions presented to the user.
